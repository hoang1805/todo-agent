> **Document purpose:** This markdown file is intentionally long and structured for Retrieval-Augmented Generation (RAG) testing. It contains fictional but realistic operational, technical, policy, and project information about a company called **Northwind Digital**. The document includes repeated concepts, cross-references, dates, exceptions, tables, and nuanced requirements so that retrieval quality can be tested across easy, medium, and difficult questions.

## 1. Company Overview

Northwind Digital is a fictional software and operations company that provides cloud-based logistics, inventory tracking, and library asset management services for enterprise customers. The company operates across three major business units: **Platform Engineering**, **Customer Operations**, and **Data Intelligence**.

The company’s internal mission is: **"Make enterprise operations predictable, observable, and easy to improve."** This mission appears in onboarding presentations, quarterly planning documents, and the engineering principles handbook. Employees are encouraged to use the mission as a decision-making filter when choosing between speed, reliability, and maintainability.

Northwind Digital was originally founded as a consulting group, but it later transitioned into a product company. Its main platform, **ArborFlow**, helps organizations manage digital assets, workflow approvals, structured metadata, file attachments, and operational audit trails. ArborFlow is used by logistics managers, component librarians, compliance officers, and support engineers.

The company has a strong documentation culture. Every major feature is expected to include a design note, API contract, test checklist, and operational runbook. Documentation is stored in an internal knowledge base called **Compass**, while source code is stored in Git repositories managed by the Engineering Productivity team.

## 2. Product Suite

Northwind Digital maintains four major internal and customer-facing products.

### 2.1 ArborFlow

ArborFlow is the flagship product. It manages library objects, image metadata, file groups, approval workflows, and search indexes. It contains both frontend and backend services.

Important ArborFlow modules include:

- **Library Management:** Stores approved library objects such as symbols, decals, packages, reference designs, and component definitions.
- **Library Request Management:** Handles draft or pending objects before they are approved into the official library.
- **Image Management:** Stores image records and connects images to one or more library objects.
- **File Component:** Handles file upload, download, preview, and token-based access.
- **Dynamic Property Rendering:** Renders dataset-driven input fields on create, edit, and detail screens.

ArborFlow has two main environments:

1. **Staging**, used for integration testing and customer acceptance testing.
2. **Production**, used by real customers and monitored continuously.

The staging environment is refreshed from sanitized production data on the first Monday of each month. Refreshes must exclude personal data, direct customer secrets, and access tokens.

### 2.2 Beacon

Beacon is the observability portal used by support engineers and service owners. It collects application logs, API latency metrics, database connection statistics, and queue processing results. Beacon does not store customer file contents; it only stores operational metadata.

Beacon has three severity levels for incidents:

- **SEV-1:** Full production outage or major data loss risk.
- **SEV-2:** Significant customer impact with workaround available.
- **SEV-3:** Minor issue, degraded experience, or internal-only operational problem.

### 2.3 Atlas Sync

Atlas Sync is a batch processing service that synchronizes library data between customer systems and ArborFlow. It supports scheduled jobs, manual re-runs, and partial retry by object identifier.

Atlas Sync uses the following retry policy:

- Network timeout: retry up to **3** times.
- Validation failure: do **not** retry automatically.
- Database deadlock: retry up to **2** times with exponential backoff.
- Authentication failure: stop immediately and alert the integration owner.

### 2.4 Meridian Reports

Meridian Reports generates weekly and monthly operational reports. It is mostly used by customer success managers, project managers, and compliance reviewers. Reports include system availability, object approval times, rejected requests, file attachment growth, and search-index rebuild statistics.

Monthly compliance reports must be generated by the **third business day** of the following month. Weekly operational reports are generated every Monday at 07:00 server time.

## 3. ArborFlow Architecture

ArborFlow follows a layered architecture:

1. **Frontend layer:** React-based web application.
2. **API layer:** Java Spring Boot services.
3. **Persistence layer:** PostgreSQL database.
4. **File storage layer:** Object storage with file group references.
5. **Search layer:** Indexing service used for quick lookup and filtered search.
6. **Batch layer:** Scheduled jobs for synchronization and cleanup.

The frontend never directly accesses the database or object storage. It communicates with the API layer through authenticated REST endpoints. File previews are retrieved using short-lived access tokens issued by the file service.

### 3.1 Key Database Entities

ArborFlow uses several important database tables. The names below are fictional but intentionally similar to real enterprise naming conventions.

#### `tb_af_library_m`

Stores approved library objects. Each library object has a stable object identifier, a type code, a display name, metadata fields, and audit columns.

Important fields:

- `library_obid`: unique library object identifier.
- `library_nm`: display name.
- `library_tp_cd`: library type code.
- `org_code`: organization code.
- `status_cd`: approval status.
- `data_ins_user_id`: user who inserted the row.
- `data_ins_time`: insert timestamp.
- `data_upd_user_id`: user who last updated the row.
- `data_upd_time`: update timestamp.

The unique key for approved library objects is a combination of `library_obid` and `org_code`. This means that the same object identifier cannot be assumed globally unique without considering the organization code.

#### `tb_af_library_request_m`

Stores pending or draft library requests. A request may later become an approved library object. It shares many display and metadata fields with `tb_af_library_m`, but it also includes workflow information.

Important fields:

- `request_obid`: unique request identifier.
- `library_obid`: target library object identifier, if already assigned.
- `request_status_cd`: draft, submitted, approved, rejected, or canceled.
- `request_reason`: user-provided reason for the request.
- `approver_user_id`: assigned approver.

A library request may contain images before approval. When the request is approved, the image relationships should be copied or reassigned according to the approval flow rules.

#### `tb_af_img_m`

Stores image metadata records. It does not store the binary file itself. Instead, it references a file group object identifier managed by the File Component.

Important fields:

- `img_obid`: unique image identifier.
- `img_nm`: image name.
- `img_tp_cd`: image type code, such as `SYMBOL`, `DECAL`, `PACKAGE`, or `REFERENCE`.
- `file_gr_obid`: file group object identifier.
- `data_ins_user_id`: user who inserted the image record.
- `data_ins_user_ip`: IP address at insertion time.
- `data_ins_time`: insert timestamp.
- `data_upd_user_id`: user who last updated the image record.
- `data_upd_user_ip`: IP address at update time.
- `data_upd_time`: update timestamp.

The image name is not globally unique. It is unique only within the same image type and organization context. Therefore, a symbol named "Main Connector" and a decal named "Main Connector" may both exist.

#### `tb_af_img_obj_m`

Connects images to library objects or library requests. It supports many-to-many relationships.

Important fields:

- `img_obid`: image identifier.
- `obj_obid`: connected object identifier.
- `obj_tp_cd`: object type code, usually `LIBRARY` or `LIBRARY_REQUEST`.
- `org_code`: organization code.
- Audit columns for insert and update tracking.

A single image may be connected to multiple library objects. A single library object may also have multiple images. When displaying connected object lists for an image, the UI must clearly indicate whether each connected object is an approved library object or a library request.

## 4. Image Management Requirements

Image Management is one of the most important ArborFlow modules. It supports image upload, metadata editing, preview, and relationship management.

### 4.1 Image Record Creation

When a user creates a new image record, they must provide:

- Image name.
- Image type.
- At least one uploaded file.
- Optional description.
- Optional connected library object or request.

The uploaded file is stored through the File Component. The image metadata stores only the `file_gr_obid`, not the absolute file path. Absolute paths should not be used for business logic because file storage locations may change between environments.

### 4.2 Supported Image Types

The initial supported image types are:

| Type Code | Display Name | Typical Usage |
|---|---|---|
| `SYMBOL` | Symbol | Schematic symbol preview |
| `DECAL` | Decal | PCB footprint or layout preview |
| `PACKAGE` | Package | Physical package reference |
| `REFERENCE` | Reference Image | Additional visual documentation |

Future image types may be added through common code management. The frontend should not hard-code all display values if the common code API is available.

### 4.3 File Extension Validation

For image preview stability, the recommended allowed file extensions are:

- `.png`
- `.jpg`
- `.jpeg`
- `.gif`
- `.webp`
- `.svg`

The system may store other files through the File Component, but Image Management should validate image preview compatibility before allowing a file to be used as the primary preview file. If an unsupported file is uploaded, the user should receive a clear validation message.

Recommended validation message:

> "Only PNG, JPG, JPEG, GIF, WEBP, and SVG files can be used as image preview files."

### 4.4 Multi-Select Name Input

Some ArborFlow screens allow users to select image names using a multi-select input. The multi-select input supports both existing registered names and new unregistered names.

If a user enters a name that does not exist in Image Management, ArborFlow should create a new image metadata record only when the user saves the form. The system should not create records immediately while the user is typing, because temporary input could create unnecessary dirty data.

New image names entered from the Library create or edit form should follow these rules:

1. Trim leading and trailing spaces.
2. Reject empty names.
3. Reject duplicate names within the same selected type.
4. Create new image records on save if they do not already exist.
5. Connect the newly created images to the current library object or request.

### 4.5 Image Preview Behavior

The detail screen should display image previews when a file group exists and the file type is preview-compatible. If the file cannot be previewed, the UI should show a fallback icon and allow download if the user has permission.

Preview tokens are short-lived. A token should not be stored in the database. The frontend should request a preview token when the preview component is rendered or refreshed.

### 4.6 Connected Object List

On the Image Management detail screen, the layout is divided into three major areas:

1. **Left panel:** list of image names or search results.
2. **Right upper panel:** image preview and metadata.
3. **Right lower panel:** connected library objects and library requests.

The connected object list must show both approved library objects and library requests if both are connected. The object type should be visible to avoid confusion. For example, the same display name may exist as an approved library object and as a pending request.

### 4.7 External Upload API

ArborFlow also supports an external upload API used by integration partners. This API must follow the same data structure as the internal UI. If the internal Image Management feature stores images as independent objects connected through `tb_af_img_obj_m`, then the external API must also create image records and relationship rows using the same model.

The external upload API must not bypass validation rules. It must validate image type, file extension, organization code, and user authorization.

## 5. Dynamic Property Rendering

Dynamic Property Rendering allows screens to build input forms from dataset configuration instead of hard-coded React components.

### 5.1 Purpose

The main purpose is to reduce duplicate frontend code and ensure that fields shown on create, edit, and detail screens follow the same metadata rules.

A dataset can define:

- Field name.
- Field label.
- Field type.
- Whether the field is required.
- Default value.
- Display order.
- Common code group.
- Placeholder text.
- Validation rule.
- Visibility condition.

### 5.2 Supported Field Types

Currently supported field types include:

- Text input.
- Number input.
- Date picker.
- Date-time picker.
- Single select.
- Multi select.
- Checkbox.
- Radio group.
- Text area.
- File selector.
- Object picker.

Unsupported field types should not crash the screen. Instead, the frontend should render a clear unsupported-field placeholder for administrators, while normal end users should see a simplified read-only value if possible.

### 5.3 Default Values

Default values may come from several sources:

1. Static dataset configuration.
2. User profile information.
3. Organization-level settings.
4. API-provided defaults.
5. Previously saved object values.

When creating a new object, API-provided defaults should override static dataset defaults only when the API value is not null. When editing an existing object, previously saved values should have priority over all default sources.

### 5.4 Performance Requirements

Dynamic property rendering can be expensive if the screen loads too many fields at once. ArborFlow screens should follow these guidelines:

- Load dataset configuration once per screen and cache it during the current session.
- Avoid rendering hidden fields when the visibility condition is false.
- Use pagination or grouped sections for very large datasets.
- Debounce expensive validation calls.
- Prevent unnecessary re-rendering of unchanged field groups.

A known issue occurred when the property-with-defaults API returned all category data instead of only the required category. This caused frontend performance degradation and, in some cases, browser crashes. The correct behavior is to return only the category data needed for the current screen.

## 6. API Guidelines

Northwind Digital APIs follow REST-style conventions. All internal APIs require authentication and organization context.

### 6.1 General Rules

- Use plural nouns for resource paths when possible.
- Use HTTP status codes consistently.
- Return validation errors with field-level details.
- Do not expose internal stack traces to customers.
- Include a correlation ID in error responses.
- Avoid returning unnecessary large datasets.

### 6.2 Example API Endpoints

| Method | Endpoint | Purpose |
|---|---|---|
| `GET` | `/v1/arbor/images` | Search image metadata |
| `POST` | `/v1/arbor/images` | Create image metadata |
| `GET` | `/v1/arbor/images/{imgObid}` | Retrieve image detail |
| `PUT` | `/v1/arbor/images/{imgObid}` | Update image metadata |
| `DELETE` | `/v1/arbor/images/{imgObid}` | Delete image metadata if not locked |
| `POST` | `/v1/files/upload` | Upload file into File Component |
| `POST` | `/v1/files/preview-token` | Issue short-lived preview token |
| `GET` | `/v1/datasets/property-with-defaults` | Retrieve dynamic property metadata and defaults |

### 6.3 Error Response Format

A standard error response contains:

```json
{
  "timestamp": "2026-07-07T08:42:00+07:00",
  "status": 400,
  "errorCode": "VALIDATION_ERROR",
  "message": "One or more fields are invalid.",
  "correlationId": "corr-7f41a9",
  "fieldErrors": [
    {
      "field": "imgNm",
      "message": "Image name is required."
    }
  ]
}
```

### 6.4 Handling Empty Arrays

For fields expected to be arrays, clients should send an empty JSON array `[]` rather than an empty string `""`. Sending an empty string for an array field may cause JSON parsing errors in strongly typed backend services.

Correct example:

```json
{
  "selectedImageNames": []
}
```

Incorrect example:

```json
{
  "selectedImageNames": ""
}
```

The backend may optionally enable coercion rules, but the recommended solution is to keep the frontend payload type correct.

## 7. File Component

The File Component centralizes file upload, preview, download, virus scanning, and storage integration.

### 7.1 File Group Concept

A file group represents one or more files connected to the same business entity. Image Management stores `file_gr_obid` so that the image metadata can reference the uploaded file group.

A file group may contain multiple files, but Image Management should identify one primary preview file. If the primary file is deleted, the system should either select another compatible file or show that no preview is available.

### 7.2 Download by Token

Downloads are performed using token-based access. The frontend sends file identifiers to the API and receives a temporary download token. The token is then used to retrieve the file stream.

The token should expire quickly. The default expiration time is **five minutes**. Tokens must be scoped to the requesting user, organization, and file identifiers.

### 7.3 Preview Flow

The recommended preview flow is:

1. User opens a screen containing a preview component.
2. Frontend requests image metadata from ArborFlow API.
3. If `file_gr_obid` exists, frontend requests a preview token from the File Component.
4. File Component validates permission and file compatibility.
5. Frontend renders the preview using the tokenized URL.
6. If the token expires, frontend requests a new token.

### 7.4 Security Requirements

File access must follow these rules:

- Never expose raw storage paths to the user.
- Never store temporary tokens in persistent storage.
- Validate authorization on every token request.
- Log file access events for audit purposes.
- Block preview for file types that could execute scripts unexpectedly.

SVG files require additional sanitization before preview because SVG content may contain script-like behavior depending on renderer configuration.

## 8. Data Migration Notes

Northwind Digital is migrating some legacy systems from Microsoft SQL Server to PostgreSQL. During migration, developers must pay attention to syntax differences, data type mappings, sequence handling, and date-time behavior.

### 8.1 Common Data Type Mapping

| SQL Server Type | PostgreSQL Type | Note |
|---|---|---|
| `NVARCHAR` | `VARCHAR` or `TEXT` | Use `TEXT` for long descriptions |
| `DATETIME` | `TIMESTAMP` | Confirm timezone behavior |
| `BIT` | `BOOLEAN` | Convert `0/1` to `false/true` |
| `UNIQUEIDENTIFIER` | `UUID` | Use PostgreSQL UUID functions |
| `IDENTITY` | `GENERATED AS IDENTITY` | Prefer standard identity syntax |

### 8.2 Date-Time Rules

Date-time values should be stored consistently. If a business timestamp represents an exact event time, use a timezone-aware strategy. If it represents a local business date, do not accidentally shift it through timezone conversion.

Migration scripts must be tested with boundary dates such as month-end, leap year dates, and daylight-saving transition dates where applicable.

### 8.3 Schema Comparison

Before migration, the team compares legacy and target schemas. Differences are classified as:

- **Expected difference:** planned naming or type change.
- **Risk difference:** possible data loss or behavior change.
- **Blocking difference:** prevents migration or deployment.

Blocking differences must be resolved before the migration rehearsal can proceed.

## 9. Incident Management

Northwind Digital uses a structured incident process.

### 9.1 Incident Roles

- **Incident Commander:** coordinates the response.
- **Technical Lead:** investigates root cause and mitigation.
- **Communications Lead:** sends updates to stakeholders.
- **Scribe:** records timeline and decisions.

For SEV-1 incidents, roles must be assigned within the first **ten minutes** after declaration.

### 9.2 Communication Cadence

- SEV-1: update every 15 minutes.
- SEV-2: update every 30 minutes.
- SEV-3: update at least once per business day.

If there is no new information, the update should still state that investigation is ongoing and identify the next planned checkpoint.

### 9.3 Post-Incident Review

A post-incident review must be completed within five business days for SEV-1 and SEV-2 incidents. The review must include:

- Summary.
- Customer impact.
- Timeline.
- Root cause.
- What went well.
- What went poorly.
- Corrective actions.
- Owners and due dates.

The goal is learning and prevention, not blame.

## 10. Access Control

Access control is based on user identity, organization membership, and role assignments.

### 10.1 Roles

| Role | Permissions |
|---|---|
| Viewer | Read approved objects and previews |
| Editor | Create and edit drafts |
| Approver | Approve or reject library requests |
| Image Manager | Manage image metadata and relationships |
| Admin | Manage settings, users, and common codes |

A user may have multiple roles. The effective permission is the union of assigned role permissions, except where a deny policy explicitly blocks access.

### 10.2 Organization Context

Every request must include organization context. The organization code is used for filtering data, validating uniqueness, and scoping file access tokens.

A common mistake is to query by `library_obid` alone. This is unsafe because the approved library table uses the composite key `library_obid + org_code`.

### 10.3 Audit Logging

Audit logs must record:

- Actor user ID.
- Organization code.
- Action type.
- Target object identifier.
- Timestamp.
- Result status.
- Correlation ID.

Audit logs should not store full file contents, passwords, access tokens, or sensitive secrets.

## 11. Search and Indexing

ArborFlow uses a search index for fast lookup. The database remains the source of truth.

### 11.1 Indexed Fields

Common indexed fields include:

- Library name.
- Library type code.
- Organization code.
- Approval status.
- Image name.
- Image type code.
- Connected object identifier.
- Last updated time.

### 11.2 Rebuild Strategy

A full index rebuild is scheduled every Sunday at 02:00 server time. Incremental indexing runs every five minutes for changed objects.

If the full rebuild fails, the system continues using the previous index and raises an SEV-2 incident if search results become stale for more than two hours.

### 11.3 Search Result Consistency

Search results may lag behind database updates by up to five minutes under normal operation. Screens that require immediate consistency should read directly from the database through the API rather than relying only on the search index.

## 12. Customer Support Playbook

Support engineers use the following diagnostic process when a customer reports an issue.

### 12.1 Initial Triage

Ask the customer for:

- Organization code.
- User ID or affected role.
- Screen name.
- Approximate time of issue.
- Correlation ID, if visible.
- Expected behavior.
- Actual behavior.
- Screenshots or logs, if available.

### 12.2 Common Issues

#### Image preview does not load

Possible causes:

- Preview token expired.
- File extension not supported.
- User lacks permission.
- File group has no primary preview file.
- SVG sanitization failed.
- Browser blocked the preview URL.

Recommended first action: request a new preview token and check authorization logs.

#### Dynamic input screen is slow

Possible causes:

- Dataset API returned too many fields.
- Hidden fields are still rendered.
- Validation calls are not debounced.
- Large common code lists are loaded repeatedly.
- Browser memory usage is high.

Recommended first action: inspect the property-with-defaults API response size and confirm category filtering.

#### Duplicate image names appear

Possible causes:

- Different image types share the same display name.
- Same name exists in different organizations.
- Whitespace was not trimmed before saving.
- Search index is stale.

Recommended first action: compare `img_nm`, `img_tp_cd`, and `org_code` together.

## 13. Release Management

Northwind Digital follows a two-week release cycle for ArborFlow.

### 13.1 Release Branching

A release branch is created from the main branch on the Monday of release week. Only approved fixes may be cherry-picked into the release branch after code freeze.

### 13.2 Code Freeze

Code freeze starts every second Wednesday at 18:00. After code freeze, new features are not allowed unless approved by the release manager and product owner.

### 13.3 Deployment Windows

Staging deployment happens on Thursday morning. Production deployment happens on Friday evening if staging validation passes.

Rollback plans must be prepared before production deployment. Database migrations must include backward-compatible rollback notes when possible.

## 14. Engineering Principles

Northwind Digital engineers follow several principles.

### 14.1 Prefer Clear Contracts

APIs should have clear request and response schemas. Ambiguous payload types should be avoided. For example, an array field should always be an array, even when empty.

### 14.2 Avoid Hidden Coupling

Frontend screens should not depend on storage path details, database internals, or undocumented backend behavior.

### 14.3 Make Failures Observable

When a system fails, logs and metrics should help engineers understand what happened. Silent failures are more dangerous than visible errors.

### 14.4 Validate at Boundaries

Validation should happen at API boundaries, UI boundaries, and integration boundaries. External APIs must not bypass internal validation rules.

### 14.5 Optimize for Maintainability

Fast delivery is important, but fragile implementations create long-term cost. Teams should document tradeoffs and revisit temporary solutions.

## 15. Example User Stories

### 15.1 Create Image from Library Form

As an editor, I want to enter a new image name from the library creation form so that I can connect an image before it exists in Image Management.

Acceptance criteria:

- User can select existing image names.
- User can type new image names.
- New names are created on save, not while typing.
- Empty names are rejected.
- Duplicate names in the same image type are rejected.
- Created image records are connected to the saved library object or request.

### 15.2 Preview Image on Detail Screen

As a viewer, I want to preview an image on the image detail screen so that I can verify the image without downloading it.

Acceptance criteria:

- Preview is shown when a compatible file exists.
- Token is requested when preview is rendered.
- Expired token can be refreshed.
- Unsupported file type shows fallback UI.
- Download is available only when the user has permission.

### 15.3 Use Dynamic Fields in Design Detail

As an administrator, I want the design detail screen to use dataset configuration so that field changes do not require frontend code changes.

Acceptance criteria:

- Dataset configuration is loaded for the correct category.
- Required fields are marked clearly.
- Existing saved values override defaults.
- Unsupported field types do not crash the screen.
- Large field groups are rendered efficiently.
